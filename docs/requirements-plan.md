# EasyHostAgent 需求计划（产品与技术基线 v0.1）

> 制定日期：2026-10-27。状态：需求已形成可实施基线；尚未开发、测试或验收。本文件以本轮最新用户决策为准，发生冲突时新决策优先。
>
> 涉及仓库：`CiBeDerORG/EasyTier`、`CiBeDerORG/EasyHostAgent`、`CiBeDerORG/deploy`。
> 代码参考：EasyTier `feat/automation-center` 中已有 `easytier-web/src/deploy_agent.rs`、`restful/deploy_agent.rs`、`DeployAgents.vue`、`deploy_tasks`/ `deploy_agents` 迁移；目标集成分支以开发时实际确认的最新代码为准，不默认为 main。

## 1. 产品目标与首期范围

在 EasyTier 的「应用与服务」中，管理已有服务器设备上的 EasyHostAgent，并以 Deploy 中央商店提供的部署定义来安装、查询、配置、更新、启停和卸载 Docker 应用。EasyHostAgent 使用 Go 原生程序和 systemd 在 FnOS / 普通 Linux 宿主机运行；本期应用安装**仅支持 Docker / Docker Compose**，不将 OpenWrt 原生包管理和 Mihomo host 模式列入首期交付。

分工：
- **Deploy**：唯一的中央应用仓库，维护描述文件、脚本、Compose、模板及共享依赖。
- **EasyTier**：登录权限、服务器设备、Agent 绑定、人工刷新 Deploy 本地工作副本、商店展示、配置表单、应用实例、任务记录、EasyTier 服务及公网映射联动。
- **EasyHostAgent**：按需 HTTPS API、设备身份与配对、宿主机资源和 Docker 发现、部署包验证及执行、本地持久化任务、日志和容器管理。
- **部署资源流向**：EasyTier 管理端按需本地 `git clone/pull` Deploy；安装时只将目标应用所需的元数据、脚本、Compose、共享依赖和配置交给 Agent。Agent 不访问 GitHub、不需要 Deploy 私有仓库凭证，也不克隆整个仓库。

## 2. 已冻结的业务规则（需求条目）

| ID | 模块 | 已确认的规则 |
|---|---|---|
| R-01 | 设备与主机 | 只有 EasyTier 设备语义类型包含 `server` 才进入主机视图；复用现有设备，不另建平行设备。支持多语义类型。 |
| R-02 | 主机归属 | admin 管理全部；普通用户仅管理其 EasyTier 设备和关联应用/服务。不支持设备转移。 |
| R-03 | Agent 安装/配对 | 页面提供可复制的宿主机安装命令；用户执行后按设备 IP 主动检测，输入一次性配对码确认绑定；Agent ID 持久稳定，IP 变化后按需重新发现、验明身份并更新地址。 |
| R-04 | Agent 通信 | 仅页面/操作触发的 HTTP(S) 请求；无周期心跳、MQTT/WebSocket 长连接、自动资源上报、离线任务队列。离线操作即时失败。 |
| R-05 | 主机检测 | 进入主机/主动刷新时获取系统、CPU、内存、磁盘、网络、Docker/Compose 能力；离线时保留上次快照并标记非实时。 |
| R-06 | Agent 生命周期 | 手动在 EasyTier 页面检查与升级；执行中的任务禁止升级；升级失败保留日志与现场，**不自动回滚**。 |
| R-07 | 主机删除 | 删除 EasyTier 设备仅解绑 Agent；主机已安装程序与 Docker 应用不动；原 EasyTier 服务记录保留。旧授权失效，可用新的配对码重新绑定。 |
| R-08 | 软件根目录 | 每个主机独立配置 `SOFTWARE_ROOT`，按系统提供默认值；存在已安装应用时不可直接修改，须先手动迁移和验证后切换。 |
| R-09 | Docker 识别 | 优先按 `com.docker.compose.project` 将多个容器聚为一个应用；无 Compose 项目标识的独立容器逐个展示；不能只扫描运行中容器。 |
| R-10 | 外部应用 | 非 Deploy 安装的 Docker 应用可查看、启停、重启、查看日志；匹配 Deploy 模板且用户确认接管后才授予模板级更新、卸载、配置管理。 |
| R-11 | 应用实例 | 同一主机同一应用仅允许一个受管实例；不同主机可各安装一个。商店模板、应用实例、EasyTier 服务是不同对象。 |
| R-12 | 商店刷新 | **仅手动点击“刷新商店”** 才由 EasyTier 管理端 `git pull`；若尚无本地工作副本，该动作执行首次 clone。平时读取本地索引与已保存数据。 |
| R-13 | 应用包 | Deploy 每个应用需机器可读描述：ID、名称、适用平台、Docker/Compose 模式、表单、默认值/密钥、端口入口、动作能力、所需脚本和共享文件。部署包标明来源 commit/校验值。 |
| R-14 | 下架行为 | Deploy 下架模板后，已安装实例仍可管理；保存原部署文件与实例信息，不依赖商店持续存在。 |
| R-15 | 安装预检 | 检查 Agent 和 Docker/Compose、OS/架构、参数、目录、端口冲突；冲突时要求用户手动修改，不自动停止已有服务或选择端口。缺少 Docker 时用户可确认一键安装（仅已适配系统）。 |
| R-16 | 安装结果 | 安装不能仅凭 Shell 退出码判成功；需复查 Docker/Compose 目标项目的实际状态，输出结果、日志和可用入口（若存在）。 |
| R-17 | 保留数据重装 | 有历史数据时提供“复用旧数据 / 全新安装”；全新安装不清理旧数据，复用前检查兼容性。 |
| R-18 | 安装配置 | 用户配置按主机/应用保存，更新时保留已有值，新增字段取 Deploy 默认值；敏感字段不明文回显。当前外部 Docker 配置变更在执行 Deploy 更新时可被 Deploy 定义覆盖。 |
| R-19 | 服务端口 | 优先选择 Web 端口作为唯一自动主要服务入口；无 Web 时取其他端口列表第一个；无任何端口则不创建服务。端口、协议从应用元数据/实际配置推导。 |
| R-20 | 服务创建 | 安装成功自动创建 EasyTier 服务，存在符合条件的同一服务则优先关联，不重复创建；默认不自动公开公网。 |
| R-21 | 端口变更 | 应用配置/端口成功生效后自动修改关联 EasyTier 服务端口及其公网映射目标端口，保留公网监听端口；失败需记录未同步状态并可人工重试。 |
| R-22 | 卸载服务 | 用户卸载应用成功时删除其**全部**关联 EasyTier 服务，包括安装前手工创建后关联的服务，同时清理服务专属公网端口映射；不误删无关服务。 |
| R-23 | 外部删除 | Docker 完整查询成功并确认应用已不存在时，删除受管应用记录及全部关联服务和其专属公网映射；主机离线、查询失败、容器停止不视为“已删除”。 |
| R-24 | 数据保护 | 正常卸载默认保留数据；若选择彻底删除需二次确认，严格限定数据路径/卷归属。 |
| R-25 | 任务 | Agent 本地持久化异步任务；页面关闭不停止；以任务 ID 去重，可按需查询状态和日志；不同应用任务可并行，同应用互斥，共享配置/资源加锁。 |
| R-26 | 任务取消 | 用户可取消；尽可能在安全节点停止，不执行自动回滚，保留已产生的现场与日志。 |
| R-27 | 离线、中断 | Agent 离线不创建新任务；宿主机重启造成执行中断时标记失败、保留现场，用户手动恢复；不可自动重做旧任务。 |
| R-28 | **失败处理最终原则** | **所有操作失败就失败：不做安装、更新、取消、Agent 自升级的自动回滚，不自动清理由失败产生的容器和数据。** 展示错误、退出码、日志，允许用户人工排障/重试。此条覆盖此前关于自动回滚的所有旧方案。 |

## 3. 业务流程与验收边界

### 3.1 主机接入
服务器语义设备 → 复制安装命令 → 宿主机安装 systemd Agent → 页面按 IP 检测 → 一次性配对 → 保存设备- Agent 绑定与最后一次快照 → 打开主机详情按需查询。

### 3.2 商店安装
手动刷新中央 Deploy 工作副本 → 校验/缓存应用模板 → 选主机、选应用、填参数 → 预检 Docker/端口/路径/历史数据 → 生成**固定版本的最小依赖部署包** → EasyTier 发送 Agent → Agent 验签/校验并持久化任务 → 部署 → 查询容器状态 → EasyTier 自动创建或关联单个主要服务。

### 3.3 日常管理
打开已安装列表按需读取（不可达时展示带时间戳的缓存）；支持基础 Docker 管理、受管应用参数变更、更新、启停、卸载；同步关联服务的端口/公网目标端口；访问 Web 入口。

### 3.4 删除与退出
卸载请求明确展示“该应用关联的服务及其公网映射将自动删除”；执行成功后按 R-22 清理关联；正常卸载的数据保留选项独立处理。删除主机与删除应用是**完全不同**的动作：删除主机保留服务，卸载应用删除关联服务。

## 4. 建议的数据实体（架构实施时可调整字段）

- `HostAgentBinding`：`device_id`、`owner_user_id`、`agent_id`、`endpoint`、配对凭证密文、最近一次查询时间/结果。
- `StoreApplication`：`app_id`、`catalog_revision`、`manifest_version`、包 SHA-256、表单及端口声明。
- `AppInstance`：`instance_id`、`device_id`、`app_id`、`compose_project`、部署包版本、安装配置、管理来源、运行状态快照、部署文件位置。
- `AppServiceBinding`：`instance_id` ↔ EasyTier `service_id`；明确一对一的自动主要服务、额外历史关联关系亦必须可追踪。
- `ExecutionTask`：`task_id`、`agent_id`、应用、动作、参数摘要、状态、退出码、日志游标、起止时间、操作者。敏感参数加密且不得进日志。

## 5. 容错与一致性策略

| 异常 | 产品行为 |
|---|---|
| Agent 离线 | 使用上次快照、注明时间；禁止操作，不排离线队列。 |
| 请求超时但 Agent 可能已接收 | 任务 ID 防重复；恢复后先查询同一任务，不能盲目再执行。 |
| 任务执行失败 | 标记失败，保留现场及日志，不执行自动回滚。 |
| Agent/宿主机重启使任务中断 | 标记失败，保留现场；人工重试必须先复查 Docker 实际状态。 |
| Docker 查询错误/权限不足 | 标记状态未知，不触发“外部应用不存在”删除逻辑。 |
| Docker 确认应用确已不存在 | 按 R-23 清理应用及服务记录；公网映射清理失败须保留可见错误和补偿任务入口。 |
| 应用部署成功、服务关联失败 | 应用保留为已安装；服务关联状态标记失败并提供人工重试，不卸载应用。 |
| 应用端口调整成功、映射调整失败 | 标记服务同步异常；允许人工重试；不回滚已生效端口。 |
| 商店下架或网络不可访问 | 使用本地已缓存目录；已安装实例使用保存的部署文件继续管理。 |

## 6. 非功能约束

- 无心跳、无长连接、无后台周期同步；执行中仅用户打开页面时按需查询。
- Agent API 必须校验配对授权；主机发现接口和执行接口权限分离。传输应使用认证的 HTTPS，禁止接受任意路径或任意 Shell 命令。
- 仅允许商店 manifest 白名单内的应用和动作；部署包应有 hash、目录穿越防护、文件大小和依赖边界校验。
- EasyTier 用户权限采用 admin 全部、普通用户所属设备及应用/服务，不增加复杂的 RBAC。
- 不引入 Redis、MQTT、消息队列或额外业务数据库服务器；EasyTier 复用现有 SQLite，Agent 可使用本地 SQLite 持久化。
- 所有删除和服务公网规则变更遵守既定业务规则，且保留审计日志。

## 7. 首期验收门槛

A. 一台 FnOS：从服务器设备完成 Agent 安装与一次性配对，刷新后可查询 CPU/内存/磁盘及 Docker 状态。
B. 已有 Docker Compose 项目归为一个应用，独立容器单独展示；外部应用支持有限管理并能安全接管。
C. 手动刷新商店后，用 Deploy 安装 Portainer；修改端口、处理冲突，完成安装实际校验并创建 EasyTier 主要服务。
D. 用户重开页面能查同一任务日志；安装/更新失败保留现场，不自动回滚；中断任务需人工恢复。
E. 应用更新保留用户配置；端口改变同步服务及既有公网目标端口；卸载按规则清理关联服务且默认保留数据。
F. Agent 离线展示缓存，不误删；Docker 查询确认应用外部删除后自动清理关联服务和专属映射。

## 8. 本期不做

Docker/Compose 以外的应用运行时、OpenWrt 包管理应用、一台主机同应用多实例、定时同步商店、Agent 心跳、自动批量部署、自动回滚、自动升级应用、通用 Shell 远程控制台、复杂权限角色管理。

## 9. 代码现实与集成注意

- EasyTier `feat/automation-center` 已有独立 Agent 连接记录、部分按需 HTTP 查询和任务日志接口，应**改造复用**，避免并行新建同功能服务；其当前端点/Token 手工登记机制不同于最终的“一次性配对+按设备绑定”。
- EasyTier 资产模块存在设备、服务、服务绑定和公网发布 API，应使用现有业务服务层修改服务，不让 Agent 操作 EasyTier 数据库。
- Deploy 当前 `deploy.sh` 支持 `list/install/update/sync`，但没有统一卸载/健康检查/应用 metadata 协议；安装包必须包含所需共享库、配置模板及应用目录，而非只传单个 `install.sh`。
- 首先验收 FnOS + Portainer，再验收多容器应用 Sub2API。开发分支应在动工前核对实时 HEAD，不能将历史分支视为已合并。
